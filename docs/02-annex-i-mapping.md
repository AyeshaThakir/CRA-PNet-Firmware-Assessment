# 02 — Annex I Requirements Mapping

Maps Annex I of Regulation (EU) 2024/2847 to the hypothetical PROFINET IO-Device firmware defined in [01-scope.md](01-scope.md).

Tags: **[V]** verified from a cited source, **[A]** assumption about the hypothetical product, **[P]** proposed control. This is a proposed mapping, not a claim that any real product implements these controls. Nothing in this repository was tested.

**Review status:** each row was worked through point by point by the author and corrected where the first draft was wrong. "Author-reviewed" means the author has explained and agreed the row; the exact wording and point numbers have **not yet** been checked against the Annex text.

**Who owns it [A]:** *Product vendor* means the manufacturer of the hypothetical firmware is responsible and P-Net is not the main factor. *Shared* means P-Net, as a component, contributes (for example how robustly it handles network input, or which protocol services it provides) and the vendor remains responsible for the product as a whole. P-Net is a software library, not a device, so Annex I applies to the firmware that integrates it. These assignments are modelling choices, not statements about what any real supplier does.

| I(1) | Appropriate level of cybersecurity based on the risks; the manufacturer's risk assessment (Art. 13(2)) decides which controls apply and how strongly | Product vendor (P-Net findings feed the assessment) | Security level follows from a documented risk assessment of the device in its industrial setting; the assessment is part of the technical documentation | Threat model and risk register drive control selection (`05`, `06`) | Risk assessment, technical documentation | Author-reviewed |

P-Net is a library and does not disable ports; the vendor's firmware does | Minimal default services; factory reset that restores the secure baseline | Default-configuration spec, reset test record | Author-reviewed |
| I(2)(c) | Security updates can be received and installed; automatic by default where appropriate with an opt-out; users are notified and can postpone temporarily | Product vendor (P-Net releases are inputs) | The device has an update mechanism. | I(2)(d) | Protection against unauthorised access (authentication, identity and access management) and reporting of possible unauthorised access | Product vendor | Management interfaces need authentication and role-based permissions; local and debug interfaces are disabled or protected. Site physical security and central identity servers are the operator's responsibility | Unique credentials, role-based access, logging of failed attempts | Access-control design, test records | Author-reviewed |
| I(2)(e) | Confidentiality of stored, transmitted and processed data (for example encryption) | Product vendor | Credentials, keys, configuration and management traffic are protected. Real-time cyclic I/O data is assumed unencrypted because of timing limits, with network segmentation as the mitigation **[A]** | Encrypt what is sensitive; document where encryption is not applied and why | Data inventory, rationale record | Author-reviewed |
| I(2)(f) | Integrity of data, commands, programs and configuration against unauthorised manipulation, with reporting of tampering | Product vendor | Firmware and configuration cannot be altered unnoticed | Signed firmware verified at boot and update; integrity check of configuration; logs forwarded off the device; failed checks logged | Integrity-mechanism design, test records | Author-reviewed |
| I(2)(g) | Process only adequate, relevant and necessary data (data minimisation) | Product vendor | The device keeps only cyclic I/O data, configuration and security logs; no personal data, location or long histories | Define and limit stored and transmitted data | Data inventory | Author-reviewed |
| I(2)(h) | Protect availability of the essential function, including after an incident, with resilience and denial-of-service mitigation | Shared: P-Net handles protocol input; vendor adds recovery | The essential function is the cyclic I/O exchange with the controller. A crash makes the controller's watchdog time out and the connection drop (CVE-2025-32405, see `03`) | Robust handling of malformed network input; watchdog and recovery to a safe state | Robustness test plan and results, recovery design | Author-reviewed |
| I(2)(i) | Minimise negative impact on other devices and networks | Shared: P-Net protocol behaviour; vendor network configuration | A misbehaving device should not flood the network or consume excessive capacity | Bounded network traffic; fail to a quiet, safe state | Network behaviour test records (a manufacturer would produce these; nothing is tested here) | Author-reviewed |
| I(2)(j) | Limit attack surfaces, including external interfaces | Shared: P-Net defines the protocol services; vendor chooses what is enabled | Only wired Ethernet and the field-side I/O stay on; USB, serial and debug ports, remote shells and web services are off by default. The services that must stay on (RPC, discovery) are hardened and robustness-tested | Disable unused services and ports; document each exposed interface | Interface and service list (feeds `05`) | Author-reviewed |
| I(2)(k) | Reduce the impact of incidents using exploitation-mitigation mechanisms | Product vendor (build and OS; P-Net is written in C) | Memory-unsafe code such as C can be exploited through bugs like out-of-bounds writes; mitigations make that harder and limit the damage | Compiler hardening, non-root execution, memory protections, watchdog recovery | Build configuration, hardening checklist | Author-reviewed |
| I(2)(l) | Record and monitor security-relevant activity, with a user opt-out | Product vendor | The device logs failed logins, configuration changes, update attempts, integrity-check failures and crashes | Small local log plus forwarding by syslog to the operator's SIEM | Logging spec, sample logs | Author-reviewed |
| I(2)(m) | Secure and easy removal of all data and settings, and secure transfer where data can move to another product | Product vendor | Decommissioning must not leak configuration, credentials or keys | Factory reset or secure erase of configuration, credentials and keys; documented decommissioning steps | Erase test record, user instructions | Author-reviewed |

### Assumptions to record in `07-limitations.md`

- **Automatic updates (I(2)(c)):** the CRA expects automatic security updates by default with an opt-out, unless this does not fit the product. In an industrial setting, automatic installation can be unsafe or unwanted. Here I assume the manufacturer would justify an operator-controlled install. Whether that justification is acceptable is not tested in this project. **[A]**
- **Confidentiality (I(2)(e)):** I do not assume PROFINET real-time process data is encrypted. Whether that is acceptable depends on the intended use and risk assessment. **[A]**
- **Everything above is a proposal.** None of it was tested or observed on a real device.
